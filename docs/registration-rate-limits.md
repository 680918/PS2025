# 注册预览请求次数限制

本步为新的注册预览增加本机、单进程的滚动窗口限流。仍不保存注册申请、不生成密码哈希、不创建正式账户、不发送邮件，不建立登录会话。

## 用户看到的效果

正常打开、填写和纠错方式不变。短时间操作过多时，页面显示「操作有些频繁，请稍等一下」，说明还需等待多少秒，并提供返回注册页的入口。不会回显邮箱、密码、表单凭证或来源地址。稍后重新填写时，密码需要重新输入。

等待按最早仍占用额度的请求计算，最多 60 秒；每次新请求重新计算剩余时间，不显示自动倒计时。页面不会自动刷新或自动重新提交；被拒绝的请求不再占用额度，也不会不断延长等待。

## 当前规则

使用最近 60 秒的滚动窗口，分别计算两个入口：

| 入口 | 同一来源上限 | 本服务进程总上限 |
| --- | --- | --- |
| `GET /web/register` | 30 次 | 240 次 |
| `POST /web/auth/register` | 10 次 | 120 次 |

来源取自连接的客户端地址，不包含连接端口。清除 Cookie、重新打开浏览器或更换连接端口不会重置同一来源的额度；同一网络出口的用户会共享来源额度，这些初始参数用于小规模本机验收，后续试用需按实际流量调整。

GET 和 POST 各自计数：提交过多仍可正常返回注册页；打开页面过多也不会阻止尚有效表单在 POST 额度内提交。首页、登录页、样式资源、邮箱确认入口不使用本步的注册额度。

POST 在解析请求体和校验用户填写之前计数，包括缺少防伪信息、跨站、错误格式和超长请求。超限返回 429 HTML 与整数 `Retry-After` 响应头，保留已有缓存、Referer 与嵌入保护；不设置或覆盖浏览器凭证，不执行后续字段校验、保存或发信。

## 简单与稳定的实现

`security/registration_rate_limit.py` 独立提供 `RegistrationRateLimiter.admit(client_key)`：允许时返回 0，超限返回需等待的秒数。使用单调时钟、短时间互斥锁和有界时间队列，避免系统时间校准改变等待、并发请求突破额度或来源键无限增长。过期计数在后续请求时清理，无队列服务、后台调度或新数据库表。

计数仅保存在应用实例的内存中，不记录邮箱、密码、防伪凭证或请求体；服务重启后清空。当前不是多进程共享限流，也不代替公网入口的流量保护。

本机 `python -m api.run` 明确关闭代理请求头处理，应用不会因任意 `Forwarded`、`X-Forwarded-For`、`X-Real-IP` 请求头重置来源额度。使用其他启动方式时也须保证连接来源可信。将来部署可信反向代理或多进程时，需要单独配置代理信任、真实来源、共享额度及对应部署测试，不能直接沿用当前本机规则公开服务。

此前的开发用 `POST /web/register` 仍属旧开发流程，本步不改其行为；公开前仍须关闭或保护旧入口。

## 验收

```powershell
python -m pytest tests/test_registration_rate_limit.py tests/test_registration_form.py tests/test_api_run.py -q -p no:cacheprovider
```

使用临时数据库和测试时钟，无真实等待或 SMTP。覆盖默认额度、滚动边界、等待向上取整、拒绝不延长等待、来源与总量上限、并发竞争、内存上限与清理、清除 Cookie 和伪造代理头无效、GET/POST 独立、其他页面可用及数据库不写入。

浏览器验收可在独立临时服务降低演示阈值以快速触发提示；正式代码默认阈值仍由上述 HTTP 测试逐项验证。恢复依照真实 60 秒窗口检查。

## 下一小步

建议先补「注册浏览器与待验证申请的归属关联」内部能力，让后续查询或重发只能针对该浏览器发起的申请；仍不直接开放发信。之后再连接网页申请保存、失败恢复与 SMTP。
