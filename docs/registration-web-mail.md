# 网页邮件操作与状态

本步骤把首次发送、发送进度和明确失败后的主动重试接到待验证申请等待页。普通启动仍不配置网页发信；模拟验收使用独立临时数据库、虚构资料和模拟发信器，不接触真实邮箱或现有资料。

## 用户看到的流程

1. 保存申请后，显示遮盖后的邮箱、有效期和发送按钮。
2. 点击按钮后使用 POST 发起一次发送，303 返回等待页。刷新只查询状态，不重放发送。
3. 明确失败时显示剩余等待秒数；至少间隔 60 秒，刷新后可主动重试。
4. 发送中、服务器已接收或结果不确定时，不提供重复发送按钮。已有有效邮件链接仍可确认。
5. 打开验证链接后仍需明确确认，才原子创建账户；不会自动登录。

模拟环境标注“本机模拟 · 不会发送真实邮件”，按钮使用“模拟发送”字样，模拟提交结果不会冒充真实投递。模拟状态与测试账户仅在独立临时数据库中存在。

## 安全和运行边界

- `create_app(..., registration_mail=None)` 默认关闭网页发信；不因为 `.env` 中已有 SMTP 开关而自动启用。
- 只有受信任的启动代码才能提供 `RegistrationMailConfig`：固定验证地址、已校验的 SMTP 配置、是否模拟。真实模式使用现有 SMTP 模块；模拟模式必须显式注入模拟发送器。请求、Host 和表单不能决定发信地址、授权码或收件人。
- 发送地址 `/web/register/send-verification` 仅接受有限大小、仅含 `csrf` 和 `action` 的 URL 编码 POST。收件人始终取自原申请，页面不提交或回显完整地址、密码、归属凭证或验证链接。
- 操作表单的 HMAC 绑定当前申请、HttpOnly 归属 Cookie、动作和不超过 10 分钟的期限，期限不超过原申请到期时间；不同动作、申请、浏览器和应用重启不能复用旧表单。保留同源与跨站检查，无 GET 发信。
- 邮件操作独立限流：每来源每分钟 3 次、进程总量 30 次，在读取请求体前检查。来源使用传输层地址，不信任任意转发头；查询和注册表单另有自己的配额。
- 每个应用同时最多处理 2 个网络发送，忙时返回 503 和 `Retry-After: 2`。真正发信在线程中运行，不阻塞事件循环；同一申请仍由持久事务保证只占用一次发送。
- 所有结果页禁用缓存、引用来源和第三方资源。错误不包含原始数据库或 SMTP 细节，操作故障时不作“邮件一定未发送”的保证。

状态规则详见 [邮件状态与失败重试保护](registration-mail-delivery.md)。等待秒数由服务端计算，页面不自动倒计时，到期后点击“刷新申请进度”即可获得可操作表单。

## 检验与后续

`tests/test_web_registration_mail.py` 在临时 SQLite 上覆盖完整保存、模拟发送、网页确认开户、失败重试、状态查询、并发、跨站与表单重放、限流、故障与隐私。浏览器另验收桌面和手机布局。全过程不发送真实邮件。

下一步可安排仅向本人邮箱的一次真实注册闭环验收，届时在本机安全提供授权码并明确确认发送。正式登录、密码找回、公开部署仍未开放；现有旧开发注册入口仍须在公开前关闭或保护。
