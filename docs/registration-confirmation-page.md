# 注册专用邮箱确认页

本步将已有的内部注册确认能力连接到网页，尚未连接注册申请提交或 SMTP。当前注册表单仍只检查填写，登录仍未开放；验证本步不需要填写真实邮箱或授权码。

## 用户看到的过程

1. 受信任内部流程为已有的待验证申请生成 `/web/verify-registration?token=...` 链接。
2. 打开、刷新、邮件预览和 GET 预取只显示「确认邮箱，开启成长的第一步」，不会查询或写入账户资料，也不会消耗链接。只有本人刚刚发起的注册才应确认。
3. 点击「确认邮箱并创建账户」后，才以 POST 确认。有效链接完成正式用户、原申请密码哈希、邮箱已验证标记的原子保存，并清除申请。
4. 成功页显示「账户已创建，邮箱已验证」，同时说明登录尚在准备中，不会自动登录。
5. 过期、已使用、旧链接、未知申请或邮箱已被已有账户占用时，统一显示「这个注册链接暂时无法使用」，不透露具体邮箱状态。

另有「请重新打开注册验证邮件」和「账户创建暂时无法完成」提示，分别用于浏览器确认信息失效和数据库临时故障。数据库错误返回 503，不回显错误细节，开户事务全部回退；排除故障后，在链接有效期内可以重试。

页面沿用知行的暖白、绿色卡片样式，适配桌面与窄屏手机。不展示邮箱、用户编号、密码、哈希或学习记录。

## 请求保护

复用既有邮箱确认页的轻量请求保护，只维护一套校验逻辑；两个流程使用不同的路径、Cookie、签名上下文和确认函数。

- 表单凭证绑定链接和当前浏览器，有效 10 分钟，使用 HttpOnly、SameSite=Strict 和路径限定，在 HTTPS 下设置 Secure。
- 拒绝跨站、缺少浏览器凭证、篡改、字段重复、超长请求和不支持的请求格式；错误页不回显提交内容。
- 兼容 `no-referrer` 下浏览器的 `Origin: null`，仍必须有正确的签名 Cookie 和表单凭证；显式跨站请求始终拒绝。
- 禁用页面缓存、Referer、外部资源与嵌入框架；成功或链接不可用后清除该流程的确认 Cookie。
- 服务重启或旧标签页失效时重新打开邮件即可，邮件链接仍按原到期时间判断。现阶段用于本机单进程；多进程部署前需共享签名密钥与对应部署测试。
- 本机启动入口继续关闭访问日志。公开部署前还须确保代理、监控和错误记录不保存一次性链接查询串或表单凭据。

既有 `/web/verify-email` 仍只确认已存在用户的邮箱，不创建新账户。其邮件测试工具不接入新注册路径；两个流程的表单与 Cookie 不能互换。

## 验收

```powershell
python -m pytest tests/test_web_registration_verification.py tests/test_web_email_verification.py tests/test_registration_verification.py tests/test_registration_form.py tests/test_mail_test.py -q -p no:cacheprovider
```

测试使用临时数据库、测试邮箱和测试密码，阻止 SMTP。覆盖仅打开不开户、确认开户、重复与过期、旧账户保护、CSRF、跨流程替换、服务重启、真实数据库写入故障后的完整回退及重试，以及注册表单仍只读。

直接打开 `/web/verify-registration` 没有凭证会看到失效提示。完整本机预览需由内部流程在临时数据库生成有效申请和链接，不能手工把随机文字当有效链接，也不需要向真实邮箱发送邮件。

## 后续小步

本步没有新增供公众签发链接或重发邮件的接口。下一小步先补注册提交的 CSRF 与浏览器上下文，再补请求次数限制、重发与发信失败恢复，最后接入真实 SMTP。登录会话另一步实现。
